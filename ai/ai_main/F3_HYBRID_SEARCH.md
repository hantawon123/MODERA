# F3 하이브리드 검색 (BM25 + kNN) + 임계값 컷

브랜치: `feat/157-hybrid-search` · Jira: `S15P11D207-157` · 기반: `develop/ai`(full-stage 머지 포함)

기존 검색을 **BM25 단독 → 하이브리드(BM25 + 시맨틱 kNN)** 로 확장하고, **무관한 질의에는
"결과 없음"을 돌려주는 절대 임계값 컷**을 넣는다. 검색 관련 로드맵(F1~F6)의 3번째 단계다.

---

## 1. 무엇을 해결하나 (문제)

지금까지 검색은 BM25 키워드 매칭만 했다(F1 에서 nori 형태소 + `minimum_should_match` 로
과다매칭까지 잡음). 그래도 남는 한계가 둘 있다.

1. **어휘가 안 겹치면 못 찾는다.** "무선 인터넷 접속 정보"로 검색하면 "카페 와이파이 비밀번호"
   문서를 못 잡는다. 뜻은 같은데 글자가 겹치지 않기 때문이다. 사용자는 스크린샷에 적힌 단어를
   정확히 기억하지 못한다 — 자연어로 검색하고 싶어 한다.
2. **무관한 질의에도 억지로 뭔가를 돌려준다.** 여행 스크린샷이 하나도 없는데 "제주도 항공권"으로
   검색하면, 흔한 형태소가 우연히 걸린 엉뚱한 문서가 나온다. "없으면 없다고 해야" 신뢰가 간다.

F2 에서 이미 **검색용 시맨틱 벡터(bge-m3, 1024차원)를 `embedding` knn_vector 필드에 색인**해
두었다. F3 는 그 벡터를 **검색 질의에 실제로 활용**하는 단계다.

---

## 2. 무엇을 추가하나 (기능)

- **하이브리드 검색**: 같은 질의를 BM25(어휘)와 kNN(의미) 두 갈래로 던지고, 두 결과를
  **RRF(Reciprocal Rank Fusion)** 로 순위 결합한다. 어휘로도, 의미로도 잘 걸리는 문서가 위로 온다.
- **절대 임계값 컷 (억지 매칭 차단)**: 융합 전에 각 후보의 **재계산 코사인 유사도**를 보고,
  임계값 미만이면 버린다. 살아남는 후보가 하나도 없으면 **`[]`(결과 없음)** 을 돌려준다.
- **자동 폴백**: 임베딩 모델이 없거나 kNN 이 실패하면 조용히 기존 BM25 로 되돌아간다.
  검색 기능 자체는 절대 죽지 않는다(발표 안전장치).

적용 범위(하이브리드가 켜지는 조건):
- `scope=ALL` **그리고** `sort=relevance`(기본) 일 때만. 임베딩이 title+summary 기반이라
  OCR/TAG scope, 날짜/최신순 정렬에서는 의미가 없어 **기존 BM25 를 그대로 쓴다**.
- 내부 엔드포인트(`/internal/v1/search`)는 `hybrid=False` 로 **옵트아웃**한다(아래 6번).

## 3. 동작 방식 (흐름)

```
질의 q, user_id, (category/tag), size, page
        │
        ├─ 하이브리드 조건 아님(OCR/TAG scope, 필드정렬, hybrid=False,
        │   킬스위치 off, 임베딩 모델 없음)  ──►  기존 BM25 경로 (_bm25_search)
        │
        └─ 하이브리드 조건  ──►  q 를 bge-m3 로 임베딩
                                    │
                    ┌───────────────┴───────────────┐   ← msearch 1왕복
              BM25 후보풀(N)                    kNN 후보풀(N, lucene)
              user_id/cat/tag filter          knn.filter 안에 같은 filter (pre-filter 격리)
                    └───────────────┬───────────────┘
                                    ▼
                         union (image_id 로 dedup)
                                    ▼
                    ┌── 임계값 컷 (융합 前, raw 신호) ──┐
                    │ 임베딩 有: cos=dot(q,emb) ≥ 0.40 │  ← bge-m3 단위벡터라 cos=내적
                    │ 임베딩 無(레거시): BM25 최소점수  │
                    └──────────────┬──────────────────┘
                          생존자 0 → return [], 0   ← "결과 없음"
                                    ▼
                    RRF 순위결합 (각 갈래 rank 로 1/(k+rank))
                                    ▼
                    total = 생존자 수 (page 무관 고정풀)
                    page/size 로 클라이언트 슬라이싱 → hits
```

핵심 포인트:
- **코사인은 클라이언트에서 재계산**한다. OpenSearch lucene `_score`(= `(1+cos)/2`, 실측 확인)에
  의존하지 않아, space_type/엔진을 바꿔도 컷 기준이 안 흔들린다.
- **후보풀 N 은 page 와 무관한 고정값**(기본 200). 그래서 같은 질의는 어느 페이지를 봐도
  `total` 이 같다. (page 에 비례해 풀을 키우면 페이지마다 total 이 달라져 UI 의 totalPages 가 흔들린다.)

## 5. 새 설정 (config.py, F5 튜닝 대비)

| 환경변수 | 기본값 | 의미 |
| --- | --- | --- |
| `SEARCH_HYBRID_ENABLED` | `true` | 전역 킬스위치. 문제 시 즉시 BM25 로 되돌린다. |
| `SEARCH_RRF_K` | `60` | RRF 상수 `1/(k+rank)`. 관례값. 상위 급경사를 원하면 낮춘다. |
| `SEARCH_HYBRID_POOL_SIZE` | `200` | 후보풀 N = kNN k. **page 무관 고정**. 융합 total 상한은 약 2N. 코퍼스가 커지면 늘린다. |
| `SEARCH_KNN_MIN_COSINE` | `0.50` | **억지 매칭 차단의 핵심**. 재계산 코사인이 이 값 미만인 후보는 버린다. A/B 로 0.50 캘리브레이션(아래 8번), 실데이터로 F5 재확정. |
| `SEARCH_BM25_MIN_SCORE` | `0.0`(off) | 임베딩 없는 레거시 문서 전용 어휘 컷. 기본 off = 하위호환. |

## 6. 설계 결정과 근거

- **왜 RRF(순위결합)인가**: BM25 `_score`(무한대 스케일)와 kNN 유사도는 스케일이 달라 그냥 못 섞는다.
  RRF 는 **순위(ordinal)만** 쓰므로 정규화 없이 안전하게 합쳐진다.
- **왜 neural-search 플러그인(하이브리드 쿼리)을 안 쓰나**: 서버에 `opensearch-neural-search` 가
  깔려 있어 `hybrid` 쿼리 + normalization-processor 를 쓸 수도 있다. 하지만 그 정규화는
  **질의마다 최고점을 1.0 으로 만들어** 절대 임계값이 사라진다 → **"결과 없음" 판정이 불가능**해진다.
  F3 의 핵심이 억지 매칭 차단이라, **raw 점수를 그대로 볼 수 있는 클라이언트측 융합**을 택했다.
- **왜 컷을 raw 코사인에 거나**: RRF 값은 절대 스케일이 없어 "0.4 미만이면 컷" 같은 절대 판정이 불가능하다.
  그래서 **융합 전에 raw 코사인**(및 레거시는 raw BM25)에 컷을 건다.
- **왜 코사인 게이트를 BM25 로 걸린 문서에도 적용하나**: 어휘 75%만 우연히 겹치고 의미상 무관한
  문서를 걸러야 억지 매칭이 진짜로 차단된다. 임베딩이 있는 후보는 BM25 로 왔든 kNN 으로 왔든
  코사인 게이트를 통과해야 한다. (트레이드오프: 짧은 키워드 질의에서 정밀도↑·재현율↓ →
  **F4 질의 라우팅**이 짧은 키워드를 BM25-only 로 보내 보완하고, 임계값도 보수적으로 시작.)
- **왜 msearch 1왕복인가**: BM25·kNN 을 `.search()` 2번 대신 `_msearch` 1왕복으로 받는다.
  부분 실패(kNN 만 실패)는 이미 받은 BM25 응답을 재사용해 처리하므로 재요청 낭비가 없다.
- **왜 내부 엔드포인트는 옵트아웃하나**: `/internal/v1/search` 는 Spring/내부 소비자용이라
  **정확한 total 과 BM25 점수 스케일**이 필요할 수 있다. 하이브리드는 total 이 근사(생존자 수)이고
  score 가 RRF 스케일이라, 내부 경로는 `hybrid=False` 로 기존 동작을 보장한다.

## 7. 하위호환 · 안전장치

- **레거시 BM25 경로 무변**: `_bm25_search` 는 기존 본문 그대로다. OCR/TAG/STRUCTURED scope,
  필드 정렬, 내부 엔드포인트, 모델 없음 → 전부 **기존과 100% 동일**(정확 total·서버 페이징·BM25 스케일).
- **임베딩 없는 문서**: 빈 OCR·F2 이전 문서는 kNN 인덱스(HNSW)에 애초에 없어 자연 제외되고,
  코사인 게이트도 면제(BM25 최소점수만) → 여전히 BM25 로 검색된다.
- **다단 폴백**: ①임베딩 None → BM25, ②하이브리드 중 예외 → BM25, ③msearch 의 BM25 서브 실패 →
  BM25, ④kNN 서브만 실패 → 받아둔 BM25 로 BM25-only 하이브리드(재실행 없음, 1회 WARNING).
- **사용자 격리**: BM25·kNN 양쪽이 같은 `_search_filters(user_id, category, tag)` 를 쓴다.
  kNN 은 `knn.filter` **안**에 user_id term 을 넣어 **pre-filter** 로 격리한다 → 타 사용자 벡터가
  결과에 섞이지 않는다. lucene filter 미지원 빌드면 조용히 새는 게 아니라 **에러 → BM25 로 degrade** 다.

## 8. 검증 현황

**실물 검증 완료** (로컬 OpenSearch 2.17.0, lucene knn):
- ✅ kNN + `knn.filter` 쿼리 문법 유효 (status 200).
- ✅ **사용자 격리**: user_id filter 로 타 사용자 문서 제외 확인(pre-filter 동작).
- ✅ **score 공식**: lucene cosinesimil `_score = (1+cos)/2` 실측 확인 → 클라 재계산 근거.
- ✅ 편집 3파일 `py_compile` 통과(full-stage 머지 반영 후에도).

**시맨틱 A/B 완료** (테스트 인덱스 12문서, bge-m3, `SEARCH_KNN_MIN_COSINE=0.50`):
- ✅ **하이브리드 recall 우위**: "무선 인터넷 접속 정보"→BM25 `[]`·하이브리드 `[101]`(와이파이, cos 0.53),
  "반려견 병원 진료"→BM25 `[]`·하이브리드 `[109,103]`(강아지 동물병원, cos 0.55), "숙소 근처 밥집"→
  BM25 `[]`·하이브리드 `[105]`(맛집, cos 0.52). **어휘 안 겹쳐도 의미로 잡음.**
- ✅ **억지 매칭 차단**: "제주도 항공권 예약 내역"·"게임 아이템 결제"(무관) → 하이브리드 `[] total=0`.
  무관쌍 코사인이 0.44~0.45 로 0.50 미만이라 전부 컷.
- ✅ **정밀도**: 관련쌍만 남고 노이즈(cos 0.40~0.41) 제거됨.
- ✅ **페이징 안정성**: 질의 "예약" page0/page1 `total=9` 동일. **폴백 패리티**: `hybrid=False` BM25 동일.
- ✅ **임계값 캘리브레이션**: 관련쌍 최상위 0.52~0.64 vs 무관쌍 최상위 0.44~0.45 → 0.50 이 최적 분리점.

> 로컬 `screenshot_kb`(데모 19개)는 F2 이전 스키마라 `embedding` 이 비어 있어, A/B 는 별도 테스트
> 인덱스(`screenshot_kb_f3ab`)에 임베딩과 함께 시드해 돌렸다(데모 인덱스 보존, 테스트 후 삭제).
> **남은 것**: 실서버 실데이터로 임계값 재확정(F5), 실 Gemini 분석 텍스트 기준 재현성 확인.
