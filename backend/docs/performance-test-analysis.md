# Modera 백엔드 성능 테스트 분석

## 1. 문서 목적

이 문서는 현재 배포된 Modera 백엔드에 대해 수행한 k6 부하 테스트, 과부하 테스트, 사용자 플로우 테스트의 조건과 결과를 기록한다.

측정 결과는 테스트 당시의 배포 버전, 서버 사양, 데이터 상태 및 네트워크 환경에 종속된다. 코드 개선 전후 비교 시에는 동일한 조건으로 다시 측정해야 한다.

## 2. 테스트 환경

- 대상 서버: `api.example.com`
- API 컨테이너: `modera-api`
- Worker 컨테이너: `modera-worker`
- 데이터 저장소: PostgreSQL, Redis, MinIO
- 부하 도구: Grafana k6 Docker 이미지
- Docker 네트워크: `infra_default`
- 내부 API 주소: `http://modera-api:8080`
- 테스트 계정: 성능 테스트 전용 계정 사용
- 관측 도구: Prometheus, Grafana, Loki

테스트 당시 k6 컨테이너와 대상 서버가 동일 호스트에서 실행되었다. 따라서 부하 생성기와 애플리케이션이 CPU, 메모리, 네트워크 자원을 공유했다. 특히 응답 크기가 큰 API는 k6 생성기 측의 처리 한계와 호스트 네트워크 경합 영향을 받을 수 있다.

## 3. 판정 기준

### 3.1 부하 테스트

API별로 다음 조건을 모두 만족하는 최대 제안 처리량을 탐색했다.

- 비즈니스 요청 p95 응답시간: 300ms 이하
- 비즈니스 요청 HTTP 실패율: 1% 미만
- 응답 상태 및 응답 envelope 검사 성공률: 99% 이상
- `dropped_iterations`: 0건

`constant-arrival-rate` 실행기를 사용했으며, 제안 처리량을 이진 탐색 방식으로 조정했다.

### 3.2 과부하 테스트

각 후보 처리량에 대해 다음 방식으로 확인했다.

- 비즈니스 부하 지속시간: 30초
- 별도 생존 확인 지속시간: 45초
- 생존 확인 주기: 1초
- 생존 확인 API: 인증된 `GET /api/v1/categories`
- 생존 확인 조건: HTTP 200 및 응답 `result == SUCCESS`
- 생존 확인 실패율: 0%
- `dropped_iterations`: 0건

과부하 처리량은 단순히 프로세스가 종료되지 않은 상태가 아니라, 30초 부하 동안 목표 요청을 드롭하지 않고 별도 생존 요청에 계속 정상 응답한 최대 제안 RPS로 판정했다.

### 3.3 결과 해상도

- 일반 조회 API 부하 테스트: 주로 100 RPS 단위
- 이미지 목록 부하 테스트: 50 RPS 단위
- 일반 조회 API 과부하 테스트: 주로 250 RPS 단위
- 이미지 목록 과부하 테스트: 100 RPS 단위

표의 최대 통과값과 최초 탈락값 사이에 실제 경계가 존재할 수 있다.

가능한 원인 후보는 다음과 같다.

- 이미지별 태그, 카테고리, 문서 및 일정 상태 조회 과정의 N+1 쿼리
- 이미지마다 수행되는 반복 `exists` 쿼리
- 엔티티 전체 조회 후 목록 DTO로 변환하는 비용
- 긴 요약 및 전체 태그를 포함한 목록 응답 크기
- 매 요청마다 수행되는 전체 건수 `COUNT(*)`
- JSON 직렬화 및 동일 호스트 네트워크 송신 비용
- 고부하 시 DB 커넥션 풀, Tomcat 스레드 또는 CPU 포화

현재 결과만으로 특정 원인을 확정할 수 없다. SQL 실행 횟수, 실행 계획, Hikari 사용량, JVM CPU와 네트워크 송신량을 같은 테스트 구간에서 추가로 대조해야 한다.

사용자 플로우는 다음 단계를 포함했다.

1. 로그인
2. 이미지 등록 및 presigned URL 발급
3. MinIO 이미지 업로드
4. 분석 완료 상태 폴링
5. 이미지 목록 조회
6. 이미지 상세 조회

- 플로우 성공률: 100%

전체 처리시간 대부분이 AI 분석 구간에서 발생했다.

### 6.2 사용자 2명, 이미지 5건

- 모든 HTTP 단계 성공
- 전체 플로우 평균: 11.64초
- 전체 플로우 p95: 14.04초
- AI 분석 평균: 11.25초

### 6.3 사용자 5명, 이미지 20건

- 모든 HTTP 단계 성공
- 전체 플로우 평균: 22.50초
- 전체 플로우 중앙값: 13.48초
- 전체 플로우 p95: 약 1분 33초
- 전체 플로우 최대: 약 1분 40초
- AI 분석 평균: 22.07초
- AI 분석 p95: 약 1분 32초

평균과 p95 차이가 매우 크며 일부 분석 요청이 약 90초까지 지연됐다. Worker 로그에서 외부 AI 서비스 `ai.example.com`에 대한 90초 read timeout과 DNS 관련 경고가 확인됐다.

HTTP 단계가 성공해도 AI 결과가 빈 값 또는 fallback 결과일 수 있으므로, HTTP 성공률만으로 분석 품질 성공률을 판단하면 안 된다. 분석 결과 상태를 `COMPLETED`, `FAILED`, `TIMED_OUT`, `EMPTY` 등으로 구분해 별도 집계할 필요가 있다.

## 7. 테스트 중 확인된 무효 결과

다음 결과는 최종 수치에서 제외했다.

### 7.1 잘못된 카테고리 정렬 파라미터

초기 대상 URL `GET /api/v1/categories?sort=name,asc`는 배포 API에서 `400 INVALID_PARAMETER`를 반환했다. 이후 정렬 파라미터를 제거한 `GET /api/v1/categories`로 정상 응답을 확인하고 다시 측정했다.

### 7.2 결과 디렉터리 권한 오류

k6 컨테이너 UID가 summary JSON 파일을 작성하지 못한 실행이 있었다. 해당 실행은 메트릭 파일이 생성되지 않아 제외했다. 이후 k6 전용 UID와 ubuntu 그룹만 쓸 수 있는 별도 결과 디렉터리를 사용했다.

### 7.3 최초 과부하 health 시나리오 오류

최초 스크립트는 `/actuator/health/liveness`를 대기 없이 반복 호출했다. 배포 서버에서 해당 경로가 정상 응답하지 않았으며 45초 동안 약 16,000회의 잘못된 health 요청이 발생했다.

해당 실행은 즉시 중단하고 결과 전체를 폐기했다. 이후 인증된 카테고리 조회를 1초마다 호출하도록 수정했고, 10 RPS 스모크 테스트에서 health 45회, 성공률 100%, 드롭 0을 확인한 후 과부하 테스트를 다시 수행했다.

## 8. 전체 백엔드 파이프라인 성능 테스트

### 8.1 테스트 범위

조회 API 중심의 기존 시험과 별도로 다음 비동기 처리 경로 전체를 측정했다.

```text
k6 이미지 등록
  → MinIO presigned PUT
  → MinIO ObjectCreated webhook
  → API Server의 image-analysis Stream 발행
  → Worker Server의 Redis Stream 소비
  → Mock AI HTTP 요청
  → Mock AI의 Worker callback
  → Worker DB 결과 저장
  → analysis-result Stream 발행
  → API Server 결과 소비 및 DB 반영
  → k6 이미지 상세 조회 성공
```

실제 AI 모델과 LLM은 호출하지 않았다. `modera-mock-ai`가 실제 `/internal/v1/analyze` 요청 계약을 받고 202를 반환한 뒤, 10ms 후 실제 Worker callback URL로 결정적인 완료 결과를 전송했다. 따라서 외부 AI 토큰은 사용하지 않으면서 AI HTTP 통신, callback 및 이벤트 버스 후속 처리는 시험 범위에 포함했다.

Worker는 시험 중에만 다음 설정으로 재생성했다.

```text
ANALYSIS_CLIENT=fastapi
AI_SERVER_URL=http://modera-mock-ai:8000
```

시험 종료 후 `AI_SERVER_URL=http://ai-ai-service-1:8000`으로 원복하고 Mock AI 컨테이너를 제거했다.

### 8.2 전체 파이프라인 부하 테스트 기준

- 부하 지속시간: 후보별 30초
- 이미지 크기: 23,924 bytes
- Mock AI 지연: 10ms
- 전체 완료시간: 이미지 등록 시작부터 API 상세 조회가 200을 반환할 때까지
- 전체 완료시간 p95: 300ms 이하
- 파이프라인 성공률: 99% 이상
- timeout: 0건
- dropped iteration: 0건

### 8.3 전체 파이프라인 부하 테스트 결과

| 제안량 | 완료 건수 | 완료 처리량 | 전체 p95 | 성공률 | 드롭 | 판정 |
|---:|---:|---:|---:|---:|---:|---|
| 1 jobs/s | 30 | 0.99 jobs/s | 97.55ms | 100% | 0 | 통과 |
| 5 jobs/s | 150 | 4.94 jobs/s | 92ms | 100% | 0 | 통과 |
| 10 jobs/s | 301 | 9.89 jobs/s | 87ms | 100% | 0 | 통과 |
| 20 jobs/s | 601 | 19.74 jobs/s | 96ms | 100% | 0 | 통과 |
| 30 jobs/s | 901 | 29.56 jobs/s | 261ms | 100% | 0 | 통과 |
| 35 jobs/s | 1,051 | 34.50 jobs/s | 279.5ms | 100% | 0 | 통과 |
| 40 jobs/s | 94 | 2.27 jobs/s | 11.23초 | 10.29% | 288 | 탈락 |
| 50 jobs/s | 32 | 0.78 jobs/s | 11.15초 | 2.83% | 373 | 탈락 |

0.3초 기준을 만족한 최대 확인 처리량은 **35 jobs/s**다. 35에서 40 jobs/s 사이에 급격한 포화 절벽이 발생했다.

40 jobs/s 시험에서 HTTP 요청 자체의 실패율은 0%였지만 최종 결과 이벤트 반영이 지연되면서 k6 VU가 상태 폴링에 묶였다. 이로 인해 pipeline timeout과 dropped iteration이 함께 증가했다.

시험 직후 Redis 상태는 다음과 같았다.

- `image-analysis`: pending 0, lag 0
- `analysis-result`: pending 9, lag 12
- 약 20초 후 `analysis-result`: pending 0, lag 0

Worker가 `image-analysis` 입력을 소비하는 구간보다 API Server가 `analysis-result`를 소비하고 read model DB에 반영하는 구간이 먼저 밀렸다. 40 RPS 이상에서도 컨테이너는 종료되지 않았으며 backlog는 부하 종료 후 해소됐다.

### 8.4 전체 파이프라인 과부하 테스트 기준

- 파이프라인 부하: 각 후보를 30초간 적용
- 별도 health 검사: 45초간 초당 1회
- health 대상: 인증된 카테고리 조회
- health 성공률: 100%
- 시작된 파이프라인 성공률: 100%
- dropped iteration: 0건
- API Server, Worker Server 및 Redis Stream 처리 경로 생존

### 8.5 전체 파이프라인 과부하 테스트 결과

| 제안량 | 완료 건수 | 전체 p95 | 성공률 | health | 드롭 | 판정 |
|---:|---:|---:|---:|---:|---:|---|
| 20 jobs/s | 601 | 148ms | 100% | 45/45 | 0 | 통과 |
| 25 jobs/s | 750 | 270.54ms | 100% | 45/45 | 0 | 통과 |
| 26 jobs/s | 299 | 10.84초 | 47.61% | 45/45 | 153 | 탈락 |
| 27 jobs/s | 807 | 1.99초 | 100% | 45/45 | 3 | 탈락 |
| 30 jobs/s | 348 | 10.70초 | 48.06% | 45/45 | 177 | 탈락 |
| 35 jobs/s | 77 | 11.22초 | 9.61% | 43/43 | 249 | 탈락 |

30초 과부하 중 서버가 생존하면서 요청을 드롭하지 않고 전체 파이프라인을 끝까지 처리한 최대 확인 처리량은 **25 jobs/s**다.

모든 후보에서 health 성공률은 100%였으므로 서버 프로세스 생존 한계는 35 jobs/s보다 높다. 그러나 26 jobs/s부터 완료율 또는 드롭 조건을 만족하지 못했으므로 “처리 가능한 최대 처리량”은 25 jobs/s로 판정했다.

26과 27 jobs/s의 결과가 단조롭지 않다. 시험이 연속 실행되면서 수천 건의 이미지, 분석 작업 및 결과 데이터가 추가됐고 후보별 시작 시점의 DB와 JVM 상태가 달랐기 때문이다. 최종 기준값으로 확정할 때는 초기화 가능한 전용 데이터셋에서 각 후보를 3회 반복하고 중앙값을 사용해야 한다.

### 8.6 파이프라인 시험 후 상태

시험 종료 전 두 Redis Stream 모두 pending 0, lag 0으로 회복된 것을 확인했다. API Server와 Worker Server는 시험 중 종료되지 않았다. Worker는 실제 AI 주소로 원복하면서 정상적으로 한 차례 재생성됐다.

성능 시험이 생성한 이미지 및 분석 데이터는 자동 삭제하지 않았다. 삭제는 테스트 계정의 기존 데이터까지 포함할 위험이 있으므로 별도 식별 조건과 승인 후 수행해야 한다.

## 9. 병목 분석 및 개선 후보

### 8.1 이미지 목록 조회

우선 확인할 항목은 다음과 같다.

1. 요청 1회당 SQL 실행 횟수 및 N+1 여부
2. 이미지별 태그, 문서, 일정 상태를 조회하는 반복 쿼리 여부
3. 목록 조회 SQL의 `EXPLAIN (ANALYZE, BUFFERS)` 결과
4. 사용자 및 정렬 컬럼 복합 인덱스 사용 여부
5. 전체 건수 count 쿼리 비용
6. DTO 변환 및 JSON 직렬화 CPU 사용량
7. 응답 크기와 네트워크 송신량
8. Hikari active, pending, acquire time
9. Tomcat active thread 및 JVM CPU

개선 후보는 다음과 같다.

- 목록 전용 Projection 또는 DTO 쿼리 사용
- 태그와 상태 정보의 N+1 제거
- 반복 `exists` 조회를 단일 쿼리 또는 일괄 조회로 통합
- 목록 응답에서 긴 summary 또는 전체 태그 제외
- `Page` 대신 `Slice` 사용으로 불필요한 count 제거
- offset 페이지네이션을 업로드 시간과 ID 기반 커서 페이지네이션으로 변경
- 실제 실행 계획을 근거로 복합 인덱스 추가

예상 인덱스 후보는 `(user_id, uploaded_at DESC, id DESC)` 형태지만, 실제 테이블 및 쿼리 조건을 확인하기 전에는 추가하지 않는다.

### 8.2 카테고리 목록

카테고리 데이터는 변경 빈도가 상대적으로 낮다면 사용자 단위 Redis 또는 로컬 캐시 적용을 검토할 수 있다. 변경 작업 시 정확한 캐시 무효화가 필요하다.

### 8.3 일정 및 문서 목록

- 사용자 ID와 조회 범위/정렬 컬럼에 대한 복합 인덱스 점검
- 목록 전용 Projection 검토
- 전체 건수 사용 여부에 따른 `Slice` 전환 검토
- 최대 페이지 크기 제한

### 8.4 AI 분석 파이프라인

- connect timeout과 read timeout 분리
- 제한된 횟수의 지수 백오프 재시도
- Circuit Breaker 적용
- Worker 동시 처리량 제한 및 backpressure
- Redis Stream lag 및 PEL 기반 부하 제어
- 분석 실패, timeout, 빈 결과의 상태 분리
- callback 저장 실패 재처리 또는 DLQ 구성

## 10. 관측성 상태

성능 분석용 Grafana 대시보드에는 다음 항목을 확인할 수 있도록 패널을 구성했다.

- 호스트 CPU, 메모리, 디스크
- API RPS, p95, p99, 오류율, 활성 요청
- Hikari 풀 사용률, pending, acquire time, timeout
- JVM heap, GC, process CPU
- Redis Stream lag, PEL, ingress
- AI 및 분석 파이프라인 지표 영역
- 오류 로그

현재 AI 서비스의 Prometheus `/metrics`가 404를 반환해 AI 컨테이너 내부 지표는 수집되지 않는다. Worker 분석 성능용 Micrometer 코드도 로컬에만 추가됐으며 원격 서버에는 배포되지 않았다. 따라서 이번 결과에는 해당 신규 Worker 메트릭이 포함되지 않는다.

## 12. 결과 해석의 제한사항

- k6와 대상 서버가 동일 호스트에서 실행됐다.
- 각 후보를 1회씩 측정했으며 3회 반복 중앙값이 아니다.
- 일부 테스트는 연속 실행되어 이전 고부하 상태의 영향을 받을 수 있다.
- API별 테스트 데이터 크기가 실제 운영 분포와 다를 수 있다.
- 조회 API 5종만 최대 처리량을 측정했다.
- 생성, 수정, 삭제 API는 데이터 변경 및 외부 AI 비용 때문에 제외했다.
- 로그인은 각 테스트의 setup 단계에서 수행했으며 로그인 API 자체의 최대 처리량은 측정하지 않았다.
- 이미지 업로드 및 AI 분석은 사용자 플로우로 측정했지만 독립적인 최대 RPS 탐색은 하지 않았다.
- cAdvisor가 배포되지 않아 컨테이너별 CPU 및 메모리 사용량을 완전히 분리하지 못했다.

최종 성능 기준을 확정하려면 별도 부하 발생기, 고정된 DB 데이터셋, API별 회복 시간, 3회 이상 반복 측정을 적용해야 한다.
