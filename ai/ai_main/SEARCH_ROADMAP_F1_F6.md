## 1. 임베딩 아키텍처 (F2~F6 공통 전제)

검색에는 **두 종류의 벡터가 완전히 분리**돼 있다. 섞으면 차원 충돌·품질 저하가 난다.

| 용도 | 모델 | 차원 | 저장 | 비고 |
| --- | --- | --- | --- | --- |
| **검색용 시맨틱** | 로컬 **bge-m3** (sentence-transformers, CPU torch, 이미지에 baked) | **1024** | OpenSearch `embedding` knn_vector | 색인·질의 같은 모델. best-effort(실패 시 BM25 폴백) |
| **카테고리 판정용** | gemini-embedding-2 | 768 | pgvector | 별개 필드·별개 모델. 이름 매칭 실패 시 코사인 최근접 |

- **왜 self-hosted(bge-m3)인가**: 발표/포폴이라 외부 임베딩 API 의존을 없앤다. 모델을 도커
  이미지에 구워(`ai-main:latest`, ~3GB) 오프라인에서도 돈다. 프로세스당 1회 로드(싱글톤).
- **knn_vector 설정**: `dimension=1024`, `method=hnsw`, `space_type=cosinesimil`, **`engine=lucene`**
  (이 빌드에서 동작 확인). 빈 OCR 문서는 벡터를 안 만들어 kNN 에서 자연 제외 → BM25 로만 검색.

## 2. F1 — BM25 과다매칭 방지 ✅ (`-156`)

**문제**: nori 형태소 분석기가 `"5만원"` 을 `5 / 만 / 원` 으로 쪼갠다. 기본 OR 매칭이라
`"원"` 같은 흔한 형태소 하나만 걸려도 무관한 문서가 대량으로 딸려온다.

**해결**: `multi_match` 에 `minimum_should_match` 를 적용해 **질의 토큰의 일정 비율 이상**이
있는 문서만 매칭한다. 기본 `75%`.

- 코드: `app/search.py` BM25 쿼리, 설정 `SEARCH_MIN_SHOULD_MATCH="75%"` (config).
- 검증: A/B 에서 한 질의의 과다매칭이 **4건 → 1건**으로 감소.
- OpenSearch 표기(`"75%"`, `"2<75%"` 등)를 그대로 받는다.

---

## 3. F2 — 검색용 시맨틱 벡터 색인 ✅ (`-158`)

**문제**: 어휘가 겹치지 않으면 BM25 로는 못 찾는다(예: "무선 인터넷" ↔ "와이파이"). 의미 기반
검색을 하려면 문서를 벡터로 색인해 둬야 한다.

**해결**: 인덱스에 `embedding` **knn_vector(1024)** 필드를 추가하고, AGENT 분석이 끝나
색인할 때 `index_document` 가 **`title + summary` 를 bge-m3 로 임베딩**해 함께 적재한다.

- 코드: `app/search.py` 의 `_index_body`(매핑 + `index.knn=true`), `index_document`(임베딩 적재),
  `app/embedder.py`(bge-m3 싱글톤, best-effort).
- 이 단계에서는 **색인만** 한다. 검색 질의에 활용하는 것은 F3.
- 검증: e2e 시맨틱 매칭 확인.
- 배포 주의: knn 필드가 추가돼, 기존 `screenshot_kb` 인덱스가 있으면 **1회 삭제 후 재생성** 필요
  (기존 이미지는 재분석해야 벡터가 채워짐). 없으면 자동 생성.

---

## 4. 태그 — 기존 태그 조회·재사용 (grounding) ✅ (`-75`)

**문제**: AGENT 가 매번 자유롭게 태그를 만들면 **의미가 같은 태그가 난립**한다
(`맛집` vs `맛집추천` vs `맛집공유`). 검색·필터·태그 목록의 품질이 떨어진다.

**해결**: 태그 생성 프롬프트에 **사용자의 기존 태그 목록을 기준점으로 주입**한다.
의미가 같으면 새로 만들지 말고 기존 태그를 재사용하도록 유도해 어휘를 수렴시킨다.

- 코드: `app/stages.py`(태그 프롬프트에 기존 태그 주입), `app/search.py` `aggregate_tags`
  (사용자 태그 집계). 카테고리의 기존 후보 제시(3단계 판정)와 같은 취지.
- 없으면 자유 생성(콜드스타트)으로 degrade — 첫 사용자도 막히지 않는다.
- 검증: 프롬프트 주입 + 29종 태그 집계 확인.

## 5. F3 — 하이브리드 검색 + 임계값 컷 🔵 (`-157`) ← 현재

**문제**: (1) 어휘 안 겹치면 못 찾음(F2 벡터를 아직 검색에 안 씀), (2) 무관한 질의에도 억지로 결과가 나옴.

**해결**: BM25(어휘)와 kNN(의미)을 **msearch 1왕복**으로 던져 **RRF** 로 순위 결합하고,
**융합 전에 raw 코사인으로 절대 임계값 컷**을 걸어 미달이면 **"결과 없음"** 을 돌려준다.

- 적용: `scope=ALL` + `sort=relevance` 에서만. 내부 엔드포인트는 `hybrid=False` 옵트아웃.
- 안전: 임베딩 없음/kNN 실패 시 BM25 로 다단 폴백. 레거시 BM25 경로·시그니처·`(hits,total)` 계약 무변.
- 설계 근거: neural-search 하이브리드는 점수를 정규화해 **절대 임계값이 사라짐** → 억지 매칭 차단이
  불가능. 그래서 **raw 점수를 볼 수 있는 클라이언트측 융합**을 택함.
- 코드: `app/search.py`(`_hybrid_search` 외), `app/config.py`(설정 5종), `app/main.py`(내부 옵트아웃).
- 상세: **[F3_HYBRID_SEARCH.md](./F3_HYBRID_SEARCH.md)**.

## 6. F4 — 질의 라우팅 ⬜ (`-159`)

**문제**: 모든 질의에 하이브리드를 쓰면, **짧은 키워드**(예: `쿠팡`)까지 임베딩·kNN 을 돌린다.
짧은 질의는 임베딩이 일반적/약해서 **정밀도가 떨어지고**(코사인 게이트에 정상 문서가 컷될 수 있음),
매 요청 임베딩 비용도 낭비다.

**해결(계획)**: 질의를 먼저 분류한다.
- **짧은 키워드성 질의** → **BM25 전용**(임베딩·kNN 스킵). 태그/정확 매칭에 강함.
- **자연어 문장성 질의** → **하이브리드**(F3).
- 판정 기준(초안): 토큰 수/공백 수/조사 유무 등 가벼운 휴리스틱. LLM 라우팅은 지연 때문에 지양.

F3 위에 얹는다. F3 의 "짧은 질의 정밀도" 트레이드오프를 구조적으로 보완하는 단계.

---

## 7. F5 — 임계값 튜닝 + 지연 측정 ⬜ (Jira 미생성)

**목적**: F3 의 컷 임계값을 데이터로 확정하고, 하이브리드 도입의 성능 비용을 계측한다.

**할 일(계획)**:
- `SEARCH_KNN_MIN_COSINE` 캘리브레이션: F3 에서 합성 12문서 A/B 로 **0.50 1차 확정**
  (관련쌍 0.52~0.64 vs 무관쌍 0.44~0.45). F5 는 **실서버 실데이터**로 재확정(0.48~0.52 구간).
- `SEARCH_RRF_K`, `SEARCH_HYBRID_POOL_SIZE` 조정.
- 지연 측정: 하이브리드 매 요청의 bge-m3 임베딩 추론 비용, msearch 왕복 시간.
- (연계) 파이프라인 구간별 소요시간 계측은 별도 트랙에서 진행 중.

## 8. F6 — 리랭크 / 태그 병합·재분류 ⬜ (`-79`, 후순위·선택)

두 갈래가 있고 둘 다 **후순위**다.

- **리랭크(검색)**: 하이브리드 상위 N 을 로컬 **크로스인코더**로 재정렬해 정밀도를 더 높인다.
  다만 크로스인코더는 실시간 지연이 커서 **기본 비활성**, 필요 시 선택 적용.
- **태그 병합·재분류(`-79`, AI2/현승준 담당)**: 이미 쌓인 태그를 사후에 군집·병합하고
  문서를 재분류한다. F(태그) grounding 이 "생성 시점" 수렴이라면, 이건 "사후 정리".
