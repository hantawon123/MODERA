# 이미지 목록·카카오 로그인 최대 RPS 재측정

> 측정일: 2026-08-04  
> 현재 버전: Git `8bc972700edc55b8c1f5ae94349520bce2570b53`, Docker `modera-api:147`  
> 이전 버전: Docker `modera-api:132`

## 1. 최종 결과

| 대상 | 최대 통과 목표 RPS | 최대 통과 실제 평균 RPS | 최대 통과 p95 | 최초 실패 RPS | 탐색 해상도 |
|---|---:|---:|---:|---:|---:|
| 현재 이미지 목록 | **370** | 367.10 | 216.03ms | 380 | 10 RPS |
| 현재 카카오 로그인 | **1,675** | 1,673.68 | 130.62ms | 1,700 | 25 RPS |
| 132 카카오 로그인 | **900** | 899.67 | 22.80ms | 925 | 25 RPS |

여기서 최대 RPS는 60초 동안 다음 조건을 모두 만족한 가장 높은 `constant-arrival-rate` 목표값이다.

- 해당 API p95 300ms 이하
- HTTP 실패율 1% 미만
- checks 성공률 99% 이상
- dropped iteration 0건

실제 평균 RPS는 setup과 전체 k6 실행시간을 포함한 요약값이므로 용량 표시는 설정한 목표 RPS를 기준으로 한다.

## 3. 현재 이미지 목록 API

### 요청

```http
GET /api/v1/images?page=0&size=20&categoryId=1744084819
```

- categoryId를 반드시 포함했다.
- setup에서 테스트 사용자를 인증하고 발급된 Access Token으로 목록을 조회했다.
- 본 부하는 60초 동안 수행했다.
- k6의 VU 부족으로 서버 한계를 과소평가하지 않도록 VU 400개를 선할당하고 최대 1,000개까지 허용했다.

### 유효 경계 결과

| 목표 RPS | 실제 평균 RPS | p95 | 실패율 | checks | dropped | 판정 |
|---:|---:|---:|---:|---:|---:|---|
| 370 | 367.10 | 216.03ms | 0% | 100% | 0 | **PASS** |
| 380 | 341.74 | 3,050.77ms | 5.39% | 94.61% | 1,285 | **FAIL** |
| 390 | 357.38 | 2,981.89ms | 2.11% | 97.89% | 894 | FAIL |
| 410 | 354.57 | 3,002.84ms | 3.16% | 96.84% | 2,291 | FAIL |
| 450 | 344.16 | 3,150.31ms | 11.18% | 88.82% | 5,335 | FAIL |

따라서 이번 DB 데이터와 서버 상태에서 이미지 목록의 최대 안정 처리량은 **370 RPS**다. 370→380 RPS의 작은 증가에서 p95가 216ms→3.05초로 급증하고 오류와 dropped가 동시에 발생했다. 포화 이후 목표 RPS를 높여도 실제 평균 처리량은 약 342~358 RPS에서 더 증가하지 않았다.

첫 탐색에서는 기본 VU 설정으로 330·340 RPS에 각각 4건·3건의 dropped가 발생했다. 두 실행 모두 p95 112ms 이하, 오류 0건이어서 생성기 VU 부족 가능성을 확인했고 최종 경계에서는 VU를 충분히 보강해 재측정했다. 최종 370/380 경계는 보강한 설정의 결과다.

## 4. 현재 카카오 로그인 API

### 요청과 계정 모델

```http
POST /api/v1/auth/kakao/login
```

- mock Kakao는 외부의 토큰 확인·사용자 정보 조회 응답만 대체했다.
- Spring의 사용자 조회, JWT 생성, Refresh Token UPSERT, PostgreSQL과 Redis 처리는 실제 코드와 실제 서비스 의존성을 사용했다.
- 사용자 번호 `10000001`부터 준비된 기존 Kakao 회원 4,000명을 순환 사용했다.
- k6의 scenario 전체 반복 번호로 계정을 선택해 동일 순간 한 계정·Refresh Token 행에 요청이 집중되는 현상을 줄였다.
- 본 부하는 각 후보 60초, VU 800개 선할당, 최대 3,000개로 실행했다.

### 경계 결과

| 목표 RPS | 실제 평균 RPS | p95 | 실패율 | dropped | 판정 |
|---:|---:|---:|---:|---:|---|
| 1,600 | 1,598.75 | 120.88ms | 0% | 0 | PASS |
| 1,650 | 1,649.52 | 81.97ms | 0% | 0 | PASS |
| **1,675** | **1,673.68** | **130.62ms** | **0%** | **0** | **PASS** |
| **1,700** | **1,643.20** | **941.09ms** | **0.014%** | **2,588** | **FAIL** |
| 1,825 | 1,337.96 | 3,067.58ms | 4.35% | 27,395 | FAIL |
| 2,050 | 1,172.69 | 3,542.01ms | 8.13% | 51,030 | FAIL |

현재 버전의 최대 안정 로그인 처리량은 **1,675 RPS**다. 1,700 RPS에서는 오류율 자체는 낮았지만 p95 300ms와 dropped 0 조건을 모두 위반했다. 포화 이후 목표 부하를 더 올리면 실제 처리량이 감소하므로 1,700 RPS 부근이 급격한 포화 시작점이다.
