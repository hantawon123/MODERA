# 카테고리 벡터 저장소

카테고리 판정에 쓰는 벡터를 AI 서버가 직접 보관하는 구조와, **아직 결정하지 않은
사안**을 남긴다. 코드는 `app/search.py`(저장소)·`app/category.py`(판정)·
`app/stages.py`(조립)에 나뉘어 있다.

## 왜 AI 서버가 갖고 있나

카테고리 판정은 요약 임베딩과 카테고리 대표 벡터의 코사인 유사도로 한다. 그 벡터를
프로세스 메모리에만 두면 재기동마다 사라지고, AGENT 가 새로 만든 카테고리도 함께
사라져 같은 카테고리를 매번 다시 만든다. Spring 이 pgvector 에 centroid 를 유지해
10-5 로 내려주는 방식(스키마의 `representativeVector`)도 가능하지만 백엔드 작업이
필요하고, AI 쪽은 이미 OpenSearch 를 쓰고 있어 자체적으로 끝낼 수 있다.

Spring 이 `representativeVector` 를 실어 보내면 그쪽이 우선한다 — 두 경로가
공존하며, 어느 쪽을 정본으로 볼지는 아래 "미결 사안"에 있다.

## 인덱스

`{OPENSEARCH_INDEX}_categories` (기본 `screenshot_kb_categories`).

본문 인덱스에 섞지 않는다. 본문 `embedding` 은 로컬 bge-m3(1024차원, 검색용),
카테고리 벡터는 Gemini(768차원, 판정용)로 **벡터 공간이 다르다**. 같은 필드에 넣으면
차원 충돌이고, 다른 필드로 넣어도 문서 성격이 달라 매핑만 지저분해진다.

| 필드 | 용도 |
| --- | --- |
| `user_id` | 사용자 격리. 전역 시드는 `0` |
| `name` | 카테고리 이름 (원본 표기) |
| `vector` | 768차원. `index: false` — kNN 없이 전량 읽어 파이썬에서 코사인 |
| `count` | centroid 에 반영된 이미지 수. 시드는 `0` |
| `model`, `dim` | 무효화 키. 임베딩 모델·차원이 바뀐 행은 조회에서 제외 |
| `updated_at` | 갱신 시각 |

`knn_vector` 를 쓰지 않는 이유: 사용자당 수십 개라 전량 스캔이 HNSW 색인·질의보다
싸다. 차원을 바꿔도 매핑을 건드릴 필요가 없다는 부수 이득도 있다.

## 문서 두 종류

### 사용자 centroid — `id = "{user_id}:{정규화이름}"`, `count >= 1`

그 카테고리로 판정된 **이미지 요약 임베딩들의 평균**. 판정이 끝나면
`upsert_category_vector` 가 누적 평균으로 갱신한다.

```
new = (기존 × count + 요약벡터) / (count + 1)
```

이미 만들어 둔 요약 임베딩(`documentVector`)을 재사용하므로 Gemini 추가 호출이 없다.
이미지가 쌓일수록 그 사용자가 실제로 그 카테고리에 무엇을 넣는지에 수렴한다.

### 전역 시드 — `id = "0:{정규화이름}"`, `count = 0`

기본 카테고리(`stages.DEFAULT_CATEGORIES` 17종) **이름 문자열**의 임베딩.
`embed(["여행"])` 같은 값이다.

이미지가 0장인 카테고리는 평균낼 것이 없어 centroid 를 만들 수 없다. 그런데 후보로는
제시해야 하므로(콜드 스타트) 이름 임베딩을 임시로 쓴다. 이 값은 사용자와 무관하게
같아서 사용자별로 복제하지 않는다 — 문서 17개로 끝난다.

`app/main.py` 의 lifespan 이 기동 시 `stages.seed_default_category_vectors()` 를
부른다. 멱등이라 이미 있는 시드는 다시 임베딩하지 않고, 조회 1회로 빠진 이름만 골라
배치로 임베딩한다. 임베딩 모델·차원을 바꾸면 조회 필터가 기존 시드를 무효로 보므로
자동으로 전량 재생성된다.

**시드가 사용자 centroid 에 누적되지 않는 것이 중요하다.** id 가 다르므로
(`0:쇼핑` vs `1:쇼핑`) 사용자의 첫 이미지는 시드를 무시하고 자기 요약 벡터로 새
문서를 만든다. 시드를 사용자 문서로 넣으면 단어 임베딩이 문장 centroid 의 1/N 로
영원히 남아, 이미지가 쌓여도 씻겨나가지 않는다 — 그래서 넣지 않는다.

### 조회 시 우선순위

`load_category_vectors(user_id)` 는 `user_id in [0, user_id]` 로 둘을 함께 읽고,
`user_id` 오름차순 정렬로 시드를 먼저 깔아 사용자 centroid 가 덮게 한다. 즉 이름이
같으면 **사용자 centroid > 전역 시드**.

## 판정 경로에서 외부 호출을 없앤 이유

`resolve_category` 는 순수 계산이다. 전에는 대표 벡터가 없는 후보를 그 자리에서
임베딩했는데(Gemini 호출), 그러면 분류 로직이 외부 장애에 묶인다. 지금은 벡터 확보가
전부 저장소 몫이고, 판정 함수는 받은 벡터로 코사인만 돈다.

벡터가 없는 후보는 코사인 0.0 으로 사실상 탈락하며(이름 완전일치로만 잡힌다),
그때 경고 로그에 이름을 남긴다. 조용히 넘기면 "왜 매번 새 카테고리가 생기는가" 를
추적할 수 없다.

## 동시성

`upsert_category_vector` 는 읽고-계산하고-쓴다. 문서 조회는 id 기반 realtime GET
이라 refresh 지연이 없고, 쓰기는 `if_seq_no`/`if_primary_term` 가드 + 409 시 읽기부터
3회 재시도다. 덮어쓰기로 넘기면 갱신 하나를 잃고 centroid 가 조용히 틀어진다.

쓰기는 `refresh=True` 다. 다음 분석은 `search` 쿼리로 후보를 읽는데 OpenSearch 는
기본 1초 주기로만 refresh 하므로, 방금 만든 카테고리가 바로 뒤 이미지의 후보 목록에서
빠진다. 문서 수십 개짜리 인덱스라 refresh 비용은 무시할 수 있다.

**남는 경쟁 조건:** 두 이미지가 *동시에* 같은 새 카테고리를 제안하면 서로를 못 본다.
저장소는 안전하지만(id 가 같아 centroid 로 합쳐진다) `categoryCreated: true` 가 같은
이름으로 두 번 콜백될 수 있다. Spring 은 이름 기준 멱등 생성이어야 한다. 이번 구조
때문에 생긴 것이 아니라 원래 있던 조건이다.

## 실패 시 동작

전부 best-effort 다. 분석을 실패시키지 않는다.

| 실패 | 결과 |
| --- | --- |
| 시드 준비 실패 | 콜드 스타트 판정이 이름 완전일치로만 동작. 다음 기동에서 재시도 |
| 조회 실패 | 빈 후보로 진행. 이름 완전일치만 동작 |
| 저장 실패 | 다음 분석이 이전 centroid 로 판정. 정확도만 떨어짐 |

# 미결 사안

## 1. 추가 카테고리 벡터를 공유할지, 사용자별로 둘지 (2026-07-29 기준 미결)

지금은 **사용자별 격리**다. 사용자1이 만든 "햄버거" 는 사용자2의 후보에 들어가지
않고, 같은 이름이라도 `1:햄버거` 와 `2:햄버거` 는 별개 문서·별개 centroid 다.

기본 17종의 이름 벡터만 전역(`user_id=0`)이고, 이건 결정된 사안이다 — 이름 문자열
임베딩이라 사용자 데이터가 0 이므로 공유해도 유출이 없다.

미결은 **AGENT 가 새로 만든 카테고리**를 어떻게 다룰지다.

### 사용자별 (현재)

- centroid = 그 사용자 이미지 요약의 평균. 그 사람이 실제로 그 카테고리에 무엇을
  넣는지에 수렴한다. 같은 "음식" 도 사람마다 다른 지점에 자리잡는다
- 개인 데이터가 다른 사용자의 판정에 섞이지 않는다
- 신규 사용자는 매번 콜드 스타트. 남이 이미 개척한 카테고리를 다시 발견해야 한다
- 문서 수 = 사용자 수 × 그 사용자 카테고리 수

### 공유

- 카테고리 어휘가 수렴한다. "햄버거"/"버거"/"패스트푸드" 로 갈라지는 것을 막는다
- 신규 사용자도 첫 이미지부터 잘 맞는 후보를 본다
- **개인 데이터 유출.** centroid 는 사용자 이미지 요약의 평균이다. 공유하면 A 의
  이미지 내용이 B 의 판정에 반영되고, 카테고리 목록 자체가 "다른 사람들이 무엇을
  저장하는가" 를 드러낸다
- 후보 목록이 무한히 길어진다. 프롬프트에 다 넣을 수 없어 상위 N 컷이 필요하고,
  그 N 을 무엇으로 정할지가 새 문제가 된다
- 한 사용자의 이상한 이미지가 전체 판정을 흔들 수 있다

### 절충안 (검토만 함, 구현 안 됨)

- **이름만 공유, 벡터는 개인화.** 전역으로 이름 목록을 모아 프롬프트 후보에는 넣되
  centroid 는 사용자별로 쌓는다. 어휘 수렴을 얻고 데이터 유출은 피한다. 사용자별
  centroid 가 없는 공유 이름은 이름 임베딩(시드와 같은 방식)으로 대체
- **사용 빈도 임계.** N 명 이상이 쓰는 카테고리만 전역으로 승격. 개인 특이 카테고리는
  개인에 남는다. 익명성은 K-익명성 수준으로 확보되지만 N 을 정하는 근거가 필요하다

### 바꿀 때 손대는 곳

- `search.load_category_vectors` — `user_id` 필터. 전역 승격 개념이 들어가면
  `terms` 목록에 승격 문서를 더한다
- `search.upsert_category_vector` — 문서 id 규칙. 공유로 가면 `{user_id}:` 접두가
  사라지거나 승격 문서를 따로 갱신해야 한다
- `stages._build_candidates` — 후보 병합·우선순위. 상위 N 컷이 필요하면 여기
- 프롬프트 — 후보 목록이 길어지면 `stages.run_agent_generation` 의 후보 전달 방식

판정 로직(`category.resolve_category`)은 후보와 벡터를 받아 코사인만 돌기 때문에
**어느 안을 골라도 바뀌지 않는다.**

## 2. `representativeVector` 정본 (백엔드 협의 필요)

`schemas.CategoryCandidate.representativeVector` 는 이미 받도록 준비돼 있고,
오면 AI 저장소보다 우선한다. 백엔드가 pgvector 에 centroid 를 유지하기로 하면 같은
값을 두 곳에서 계산하게 되므로, 어느 쪽을 정본으로 볼지 정해야 한다.

- AI 정본: 백엔드는 `representativeVector` 를 안 보낸다. 지금 상태
- Spring 정본: AI 는 저장소를 읽기 캐시로만 쓰거나 아예 지운다. `documentVector` 를
  이미 콜백으로 넘기고 있으니 백엔드가 centroid 를 만들 재료는 있다

## 3. 벡터 공간 통일 (미결)

판정은 Gemini 768, 검색은 로컬 bge-m3 1024 로 벡터가 둘이다. bge-m3 로 통일하면
카테고리 centroid 를 본문 인덱스의 `embedding` 필드에서 `category_name` terms 집계로
재계산할 수 있어 저장소 자체가 필요 없어진다. 대신 요약 임베딩을 로컬 모델로 돌려야
하고(CPU 시간), Spring 에 넘기는 `documentVector` 의 모델·차원 계약이 바뀐다.

## 4. `similarity_threshold` 0.80 의 근거 (측정 안 됨)

`SIMILARITY_THRESHOLD` 기본값 0.80 은 경험값이다. 이름 임베딩(단어)과 요약(문장)을
비교하던 시절에는 이 값을 거의 못 넘어 벡터 분기가 사실상 죽어 있었다. centroid 가
쌓이면 문장↔문장 비교라 상황이 달라지므로, 실제 데이터로 재조정이 필요하다.
`resolve_category` 가 상위 3개 유사도를 로그에 남기므로 그 값으로 판단할 수 있다.
