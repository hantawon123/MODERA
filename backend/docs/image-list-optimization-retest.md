# 이미지 목록 최적화 후 성능 재측정

> 측정일: 2026-08-03  
> 대상: 현재 배포된 `modera-api:latest`  
> 대표 요청: `GET /api/v1/images?page=0&size=20&categoryId=1744084819`

## 1. 결과 요약

| 항목 | 개선 전 | 수정 버전 | 변화 |
|---|---:|---:|---:|
| 0.3초 기준 최대 안정 처리량 | 200 RPS | **400 RPS** | **2.0배** |
| 부하 테스트 최초 실패 | 250 RPS | **450 RPS** | +200 RPS |
| 30초 과부하 최대 생존 처리량 | 200 RPS | **400 RPS** | **2.0배** |
| 과부하 최초 실패 | 300 RPS | **450 RPS** | +150 RPS |

이미지 목록 수정으로 전용 API 처리 한계는 2배 증가했다. 다만 목표인 2,000 RPS에는 아직 도달하지 못했고, 전체 사용자 흐름에서는 Hikari DB 커넥션 풀이 다음 병목으로 확인됐다.

## 2. API 부하 테스트

### 판정 기준

- p95 ≤ 300ms
- HTTP 오류율 < 1%
- checks 성공률 ≥ 99%
- dropped 0
- 단계당 60초

| 제안 부하 | p95 | 실제 총 HTTP RPS | 오류 | dropped | 판정 |
|---:|---:|---:|---:|---:|---|
| 300 RPS | 12.98ms | 298.17 | 0 | 0 | 통과 |
| **400 RPS** | **49.88ms** | **397.51** | **0** | **0** | **최대 통과** |
| **450 RPS** | **583.36ms** | **429.52** | **0** | **878** | **최초 실패** |
| 500 RPS | 675.04ms | 430.63 | 0 | 발생 | 실패 |
| 850 RPS | 1,076.14ms | 430.14 | 확인 불가 | 발생 | 실패 |
| 1,600 RPS | 2,084.96ms | 418.45 | 확인 불가 | 발생 | 실패 |

450 RPS부터 실제 처리량은 약 430 RPS 부근에서 더 증가하지 않았다. 서버가 반환한 요청은 정상 응답했지만 목표 도착률을 소화하지 못해 p95와 dropped가 동시에 증가했다.

## 3. API 과부하 테스트

### 판정 기준

- 이미지 목록 요청 30초
- health 확인 45초
- health 성공률 100%
- dropped 0
- 서버 컨테이너 생존

| 제안 부하 | 처리된 비즈니스 요청 | 전체 p95 | health | dropped | 판정 |
|---:|---:|---:|---:|---:|---|
| 350 RPS | 약 10,500건 | 별도 태그 없음 | 100% | 0 | 통과 |
| **400 RPS** | **12,000건** | **75.00ms** | **45/45** | **0** | **최대 통과** |
| **450 RPS** | **13,347건** | **637.90ms** | **38/38** | **192** | **최초 실패** |
| 600 RPS | 목표 미달 | 별도 태그 없음 | 서버 생존 | 발생 | 실패 |

450 RPS에서도 health 응답 자체는 모두 성공했지만 요청 지연 때문에 45초 동안 38회만 실행됐고, dropped 192건이 발생해 최대 생존 처리량 조건에는 실패했다.

## 4. 최신 버전 사용자 시나리오

사용자 요청에 따라 단계별 시간을 5분에서 2분으로 줄였다. 시나리오가 사용자당 최소 100회를 요구하므로 다음 조건을 사용했다.

- 시작 사용자: 125명
- 사용자당 API 호출: 100회
- 시나리오 실행 시간: 120초
- 로그인: 사용자당 1회
- 시작 분산: 10초
- 호출 간격: 약 1.2초
- AI, Worker, MinIO: 제외
- 다음 계획 단계: 130 → 150 → 175 → 200명
- HTTP 오류, 실패 사용자 또는 미완료 사용자가 처음 발생하면 자동 중단

### 125명 결과

| 항목 | 결과 |
|---|---:|
| 계획 시나리오 호출 | 12,500건 |
| 로그인 포함 비즈니스 요청 | 12,625건 |
| HTTP 오류 | **1건** |
| 완료 사용자 | 125명 |
| 무오류 사용자 | **124명** |
| 오류 사용자 | **1명** |
| 비즈니스 p95 | 164.52ms |
| 로그인 p95 | 2,737.45ms |
| 전체 평균 RPS | 90.46 |
| health | 100% |
| 판정 | **실패, 130명 단계 미진행** |

### 실패 원인

실패 요청은 다음과 같다.

```text
GET /api/v1/images 500 3967ms
CannotCreateTransactionException
SQLTransientConnectionException
Connection is not available, request timed out after 3964ms
Hikari: total=20, active=20, idle=0, waiting=54
```

이미지 목록 쿼리의 단독 처리량은 2배 증가했지만, 동시 로그인과 여러 API가 겹치는 사용자 유입 초기에 DB 커넥션 풀이 포화됐다. 같은 시점에 이미지 목록 외에도 로그인, 문서, 스케줄, 유사 이미지 요청이 2초 이상 대기했다.

따라서 최신 버전의 2분·100회 조건에서는 **125명이 무오류 통과점이 아니라 최초 실패점**이다. 1건뿐이지만 “오류 0” 기준을 적용했으므로 다음 단계로 올리지 않았다.

## 5. 중단된 5분 시도

사용자가 단계별 관찰 시간을 2분으로 변경하기 전에 125명·200회·5분 조건을 실행했다. 약 3분 후 정상 종료했을 때 다음 중간값이 기록됐다.

- 처리된 비즈니스 요청: 17,966건
- HTTP 오류: 0건
- 당시 비즈니스 p95: 23.92ms
- 당시 로그인 p95: 3,709.42ms

강제 종료 시점에 200회를 완주한 사용자가 없으므로 이 값은 통과·실패 용량 판정에 사용하지 않는다.
