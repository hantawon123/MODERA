# Mock Kakao 더미 사용자 기반 점진적 과부하 테스트 인수인계

> 최종 실행일: 2026-08-04
>
> 목적: 실제 Kakao 계정·Access Token을 사용하지 않고, 서로 다른 Kakao 사용자들이 MODERA 앱을 사용하는 상황에서 API 수정 전후 성능을 같은 조건으로 비교한다.
>
> 상태: 2026-08-04 기준 현재 이미지와 132 이미지의 최대 동시 사용자 경계를 25명 단위까지 측정 완료했다. 서버는 원본 최신 API와 실제 Kakao 설정으로 복구됐다.

## 1. 왜 mock Kakao가 필요한가

MODERA는 운영에서 카카오 로그인만 사용한다. 기존 로컬 ID·비밀번호 로그인 기반 k6 테스트는 다음 이유로 운영 사용자 흐름을 제대로 대표하지 못했다.

- 모든 VU가 동일한 `k6tester` 계정을 사용했다.
- BCrypt cost 12의 CPU 부하가 카카오 로그인에는 존재하지 않는다.
- 같은 사용자의 이미지·즐겨찾기 행을 동시에 사용해 비현실적인 DB 경합이 발생했다.
- 기존 130명 실패는 서로 다른 130명의 사용자 한계가 아니라 단일 계정 동시 사용과 로컬 로그인 부하가 섞인 결과였다.

이를 해결하기 위해 Kakao의 외부 HTTP 응답만 대체하는 `mock-kakao`를 만들었다. MODERA 내부 로직은 실제 배포 코드를 그대로 사용한다.

```text
k6
  -> POST /api/v1/auth/kakao/login
  -> modera-api KakaoClient
  -> mock-kakao 토큰 앱 ID 확인
  -> mock-kakao 사용자 정보 확인
  -> 실제 PostgreSQL 사용자 생성 또는 조회
  -> 실제 JWT 발급
  -> 실제 Refresh Token UPSERT
  -> 발급된 Access Token으로 앱 API 100회 호출
```

mock 처리 범위는 다음 두 Kakao API뿐이다.

```text
GET /v1/user/access_token_info
GET /v2/user/me
```

PostgreSQL, Redis, JWT, Refresh Token, Spring Security와 각 비즈니스 API는 mock이 아니다.

## 3. 더미 Kakao 사용자 규칙

mock token 형식은 다음과 같다.

```text
modera-perf-kakao-{userNumber}
```

예를 들어 `userNumber=3000001`이면 mock Kakao는 다음 사용자를 반환한다.

```text
token:     modera-perf-kakao-3000001
Kakao ID:  7000003000001
email:     perf-kakao-3000001@perf.modera.test
device ID: k6-kakao-device-3000001
```

VU마다 token, Kakao ID, 이메일, device ID가 다르다. 따라서 모든 사용자가 같은 사용자 행이나 Refresh Token 행을 공유하지 않는다.

완료된 비교에서는 다음 사용자 구간을 사용했다.

| 버전 | USER_OFFSET | 생성 범위 |
|---|---:|---|
| 수정 버전 `135` | 3,000,000 | health 사용자 1명 + 3,000,001~3,000,200 |
| 이전 버전 `132` | 4,000,000 | health 사용자 1명 + 4,000,001~4,000,200 |

총 약 402개의 성능 테스트 사용자가 DB에 남아 있다. 자동 삭제하지 않았다. 이메일의 `@perf.modera.test`와 provider ID 구간으로 식별할 수 있지만, FK·soft delete 정책을 확인하지 않은 직접 DELETE는 금지한다.

## 4. bootstrap과 측정을 분리한 이유

`run-kakao-user-capacity.sh`는 지정한 단계 중 가장 큰 사용자 수만큼 사용자를 먼저 준비한다.

```text
LEVELS="125 130 150 175 200"
-> 측정 전에 200명 bootstrap
-> 125, 130, 150, 175, 200명 측정에서는 모두 기존 사용자 재로그인
```

이렇게 해야 낮은 단계에서는 기존 사용자 로그인, 높은 단계에서는 신규 가입이 섞이는 문제를 막을 수 있다.

신규 가입 자체의 성능은 `kakao-user-bootstrap.js` 결과로 별도 확인한다. 사용자 시나리오 용량 측정에서는 가입 비용을 제외하고 기존 회원의 앱 재접속을 측정한다.

## 5. 사용자 시나리오

각 VU는 다음과 같이 동작한다.

1. 10초 유입 구간 안에서 무작위 시점에 진입한다.
2. VU 전용 mock Kakao token으로 로그인한다.
3. 발급받은 Access Token을 세션 동안 재사용한다.
4. 120초 동안 앱 API를 정확히 100회 호출한다.
5. 호출 간격은 평균 1.2초이며 ±30% jitter를 적용한다.
6. 별도 liveness VU가 카테고리 API를 계속 호출한다.
7. HTTP 오류, 인증 오류, 실패 사용자 또는 미완료 사용자가 발생하면 다음 단계로 넘어가지 않는다.

다섯 개 사용자 흐름을 VU에 고르게 배정한다.

| 흐름 | 호출 API |
|---|---|
| 홈 | 사용자 프로필, 카테고리, 최근 이미지 목록 |
| 갤러리 | 제목순·업로드순 목록, 페이지 이동, 즐겨찾기 필터 |
| 검색 | 키워드 이미지 검색, 카테고리, 갤러리 복귀 |
| 일정 | 전체 일정, 캘린더 등록·미등록 일정 목록 |
| 문서 | 최신순·이름순·과거순 문서 목록 |

### 현재 시나리오의 제한

더미 사용자는 신규 계정이라 분석 완료 이미지·문서·일정이 없다. 따라서 목록·COUNT·인증·페이징 경로는 실제로 실행하지만 결과 데이터는 대부분 비어 있다.

이번 결과는 다음 항목을 비교하는 데 유효하다.

- 카카오 로그인 이후 사용자 생성·조회
- JWT와 Refresh Token 처리
- 서로 다른 사용자 조건의 DB 커넥션 경합
- 데이터가 없는 신규 사용자의 기본 앱 탐색
- 수정 전후 동일 조건의 상대 성능

다음 항목의 절대 용량으로 해석하면 안 된다.

- 데이터가 많은 사용자의 이미지 목록
- 이미지 상세·유사 이미지
- 즐겨찾기 변경
- 실제 이미지 등록·MinIO·Redis 이벤트
- Worker·AI 분석

이 항목들은 사용자별 fixture 데이터 또는 별도 실제 파이프라인 시나리오가 필요하다.

## 10. 결과 해석

### 확인된 내용

- 수정 버전과 이전 버전 모두 200명까지 오류 없이 통과했다.
- 두 버전 모두 200명에서 사용자당 100회, 총 20,000건의 앱 요청을 전부 처리했다.
- 수정 버전의 단계 평균 앱 p95는 2.37ms, 이전 버전은 2.45ms다.
- 수정 버전의 단계 평균 인증 p95는 13.36ms, 이전 버전은 15.38ms다.
- 수정 버전이 앱 p95 평균 약 3.3%, 인증 p95 평균 약 13.2% 개선됐다.
- 측정 중 Hikari pending은 관측 시점마다 0이었다.
- Hikari 20과 30의 차이가 현재 부하에서는 기능 한계로 나타나지 않았다.

### 확인하지 못한 내용

- 두 버전의 최대 동시 사용자 한계
- 최초 오류 사용자 단계
- 200명을 초과한 구간의 Hikari 20/30 차이

따라서 결과를 “최대 200명”이라고 표현하면 안 된다. 정확한 표현은 다음과 같다.

```text
두 버전 모두 이번 시나리오에서 최소 200명까지 안정적으로 처리했다.
최대 용량 경계는 아직 발견하지 못했다.
```

## 11. 실제 수행 순서

이번 비교 테스트는 다음 순서로 수행했다.

1. 원본 `modera-api`의 health와 실행 중인 다른 k6가 없는지 확인했다.
2. `infra_default` 네트워크에 mock Kakao 컨테이너를 기동하고 health를 확인했다.
3. 수정 버전 `135`를 원본 컨테이너와 같은 환경변수·Firebase mount로 임시 기동했다.
4. Kakao API base URL만 mock Kakao 주소로 변경했다.
5. 수정 버전 전용 사용자 200명을 bootstrap했다.
6. 수정 버전에서 125, 130, 150, 175, 200명 순서로 측정했다.
7. 수정 버전 임시 컨테이너를 제거하고 원본 API를 복구했다.
8. 이전 버전 `132`를 같은 환경과 mock Kakao 설정으로 임시 기동했다.
9. 이전 버전 전용 사용자 200명을 다른 `USER_OFFSET`으로 bootstrap했다.
10. 이전 버전에서 동일한 125, 130, 150, 175, 200명 순서로 측정했다.
11. 이전 버전 임시 컨테이너와 mock Kakao를 제거했다.
12. 원본 `modera-api:latest`를 복구하고 DB·Redis·liveness·readiness가 모두 `UP`인지 확인했다.

두 버전의 단계, 호출 수, 실행 시간, 유입 분산, cooldown과 판정 기준은 모두 동일하게 유지했다. 버전별 사용자 번호 구간과 결과 디렉터리만 분리했다.

250명 확장 테스트는 실제 k6 실행 전에 중단했으므로 결과가 없다.

- VU마다 서로 다른 mock Kakao 계정을 사용한다.
- 가장 큰 후보 수만큼 계정을 먼저 bootstrap하고, 본 측정은 기존 회원 로그인만 수행한다.
- 사용자 한 명이 120초 동안 Spring 앱 API를 정확히 100회 호출한다.
- 홈, 갤러리, 검색, 일정, 문서의 다섯 흐름을 사용자에게 균등 배정한다.
- 사용자는 10초 동안 분산 진입하고 호출 간격에는 jitter를 적용한다.
- 별도 VU가 2분 20초 동안 서버 liveness를 확인한다.
- AI, Worker, MinIO, 이미지 업로드와 실제 시맨틱 검색은 제외한다.
- 앱 API p95 300ms 이하, 인증 p95 1초 이하를 적용한다.
- 앱 오류, 인증 오류, 실패 사용자 또는 미완주 사용자가 한 명이라도 있으면 해당 후보는 실패다.
- 각 후보 사이에 30초 cooldown을 적용한다.

초기에는 현재 버전을 300, 400, 500, 600, 700명으로 확인했다. 이후 사용자 요청에 따라 선형 증가를 중단하고 다음 방식으로 전환했다.

1. 성공 하한보다 큰 후보를 두 배 수준으로 올려 최초 실패 상한을 찾는다.
2. 성공 하한과 실패 상한의 중간값을 실행한다.
3. 결과에 따라 성공 또는 실패 경계를 갱신한다.
4. 두 경계의 차이가 25명이 될 때까지 반복한다.

실행기는 `ops/k6/run-kakao-user-capacity-binary.sh`이며 기본 탐색 해상도는 25명이다. 경계 근처 결과는 시스템 잡음에 따라 달라질 수 있으므로 절대적인 영구 한계가 아니라 이 조건에서 확인한 최대 성공값으로 해석한다.
